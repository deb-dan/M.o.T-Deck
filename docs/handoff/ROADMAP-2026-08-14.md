## 8. LOffice consolidation — DEBI'S RULING 2026-08-27: ONE EDITOR
Debi ruled the two-editor feel redundant ("we could have only the onlyoffice, but with
our ui"). Direction: ONLYOFFICE becomes THE editing surface inside the LOffice layout
(our file rail + our AI panel + our top strip stay; our menu bar/toolbar/grid retire from
the editing role). Facts settling the open questions:
- **"Once installed, why not instant like Music?" — Debi is right with one nuance:** the
  40-75s number was a COLD load (first wasm compile, empty HTTP cache). After install,
  repeat opens ride a year-long immutable cache; with a warmed editor instance kept alive
  across file switches it is effectively instant after the tab's first open. The plan:
  preload the editor when the LOffice tab opens; keep ONE editor instance and swap
  documents into it. Tier-1 grid's remaining honest role: instant landing/preview +
  the not-installed fallback + a plain-text safety hatch — NOT a parallel editor.
- **The wiped-unsaved-edits complaint dissolves** in one-editor world (no tier handoff);
  until then: drafts kept in memory across file switches + "Save & open" on handoff.
- **ONLYOFFICE's ribbon "AI" tab** (Debi saw it on their site) is their AI PLUGIN — NOT
  in CryptPad's bundle (verified: no plugins dir). It is open source (onlyoffice/
  sdkjs-plugins, api.OnlyOffice AI) and accepts OpenAI-compatible providers → vendor it
  and point it at OUR runner (:6767), exactly the Hermes/OpenCode provider pattern.
  Recon slice: pin, licence, offline-serve, provider config shape.
- **Print button** in the serverless bundle throws (expects DocumentServer) → disable
  with reason via editor config. **x2t.wasm CONTAINS PdfWriter (verified via strings)**
  → "Download as PDF" is buildable without any fork; queue with the consolidation.
  "Save as Google Sheet" = N/A locally (cloud format); export menu = xlsx/pdf (+csv?).
- COEP note for embedding: hosting the editor + our panels in ONE page means the whole
  page must be cross-origin isolated; all same-origin, so plumbing not blocker.
Sequencing: recon (AI plugin + keep-alive/preload measurement) → Fable spec → build.

main-model vision by NAME KEYWORDS ("gemma-3", "llama-4", standalone "vl") with no
capability input, and its VL describe call has a HARD-CODED 120s timeout — both upstream
defects. Our pre-caption + evidence-gated vision_model auto-wire uses only Odysseus's own
supported surfaces (its vision cache + its setting) and is the right bridge, but Debi's
ruling: **this must be REALLY addressed in the future — root cause, upstream.**

The fix when its day comes:
1. Upstream contribution (issue + PR, needs Debi's word — publishing under her account):
   capability-based vision detection (ask the server / registry what the model can do,
   not a name regex) + a configurable VL timeout (their `llm_call(..., timeout=120)`).
2. When upstream merges and we take the update: RETIRE our pre-caption shim and the
   auto-wire marker (data/ody_vision_autowire.json) — the bridge code is designed to be
   removable; test_attach_lanes_contract.py pins the upstream mechanics and will flag
   the moment an Odysseus update changes them (the pin-bump gates say exactly what to
   re-check).
Until then the bridge stands: panel attaches ~6s via pre-caption, native pixels wherever
Odysseus name-recognises the model, honest advisory when no vision path exists.

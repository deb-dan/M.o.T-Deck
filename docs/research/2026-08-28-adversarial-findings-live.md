# Adversarial QA — the LIVE LOffice surface (2026-08-28)

**What this is.** A hostile pass over the served `/office` page + the embedded ONLYOFFICE
editor + the AI panel, hunting for behaviour a normal user would call *wrong* or *a lie*.
Nothing was fixed and no existing file was edited. Everything below was measured on the
live bridge on :8700 (build `loffice-2026-08-28b`, editor `v9.2.0.119+3`) with the
WKWebView probe, against **QA copies only** — fixtures generated by
`…/scratchpad/mkqa.py`, imported as `QA-A.xlsx` / `QA-B.xlsx` / `QA-rich.xlsx`, and
deleted again through the app's own Delete route at the end of the run. Debi's own
workbooks were never opened for writing.

**Known-in-flight, deliberately skipped** (another builder is in `office_ops.py`,
`office_mcp.py`, `panel/office.html` right now): currency-text coercion, SUM-over-text
warnings, quoted text in grounding, computed receipt checks. Nothing below depends on
those.

## LIES-TO-USER

### L1 — The editor's own Save button clears "unsaved changes" without saving, and the next file switch then bins the work silently
**Severity: LIES-TO-USER (with silent data loss).** The single worst behaviour on the surface.

Repro (measured end to end, `qa-ghost2.png`):
1. Open `QA-A.xlsx`. The ONLYOFFICE header inside the centre column carries its own
   floppy-disk **Save** control (`#slot-btn-dt-save` → `button[aria-label="Save (Ctrl+S)"]`,
   visible, not disabled) next to its Undo/Redo.
2. Make an edit. Our strip is correct: dot on, `#p-file` = "unsaved changes".
3. Click **the editor's** Save icon (not ours).
4. Our strip flips to **"all changes saved"**, the dot goes out, no message anywhere,
   and the editor's own status line says `ready`. `ooChild.probe()` reports `dirty:false`.
   **The file on disk was not touched** — `mtime` identical before and after
   (1787867526 → 1787867526).
5. Click another workbook in the rail. Because `dirty` is now false, `confirmDiscard()`
   returns true immediately: **no warning, no two-step, no "Save & open"**. It just swaps.
6. Reopen `QA-A.xlsx`: the edited cell is **empty**. The work is gone.

Cause: the editor's Save runs its own DocumentServer save through
`connectMockServer`'s `saveChanges` → our mock ACKs it → sdkjs considers the document
saved and fires `onDocumentStateChange(false)` → `oo.html` forwards `{kind:'state',
dirty:false}` → the parent clears THE dirty flag that guards every discard path,
the heartbeat, and the "as last saved" note. Only `ooSave()` (our strip / File → Save /
our ⌘S) actually reaches `/api/office/writeback`.

**Correct behaviour:** the only Save control inside the LOffice window must be the one
that writes the file — either hide/disable ONLYOFFICE's own save affordances in the embed
config, or route them into `ooSave()`; a `state{dirty:false}` that no write-back produced
must never be allowed to clear the parent's dirty flag.

### L2 — "Create a spreadsheet with this data" reports six cells written and writes an empty file
**Severity: LIES-TO-USER (with total loss of the result).**

Repro (measured; `qa-create2.png`; verified on disk with openpyxl):
1. Start screen, nothing open. Quick lane. Ask for a table (any reply carrying a
   ```` ```loffice ```` block with a `file` and a `set` op).
2. The card reads: *"6 cells in a new spreadsheet called QA start create — No spreadsheet
   is open, so Apply makes one first. Nothing is written until you press Apply, and the
   file is only saved when you press ⌘S."* Button: **Create & apply**.
3. Press it. The card stamps **"change applied · Applied to Sheet1 — 6 written. The file
   is NOT saved yet — press ⌘S."** and the strip says *"6 cells in Sheet1 — applied.
   Press ⌘S to save it to the file."*
4. What you are looking at — the editor, which came up on the new file — shows
   **A1, A2, B2 all empty**. The dot is **off** and the strip says **"all changes saved"**.
5. Do as told and press ⌘S. Strip: *"Saved QA start create.xlsx — 7 KB"*.
   On disk: `dims A1:A1`, every cell `None`. **The six cells never existed in any file.**

Cause: `actApply()` checks `editorActive()` at its top — before the workbook exists — so
the `!current` branch runs the TIER-1 writer (`actRunOps` into `snap`) while
`create()`→`openDoc()`→`showWorkbook()` brings the editor up on the file as created
(empty). `ooEvent('ready')` then sets `dirty=false`, and the ⌘S the card asked for goes
through `ooSave()`, writing the editor's empty document. Three separate surfaces state a
success that no file ever had.

**Correct behaviour:** on the create-then-write path the ops must run through the editor
once it holds the new file (or the tier-1 write must be saved and the editor opened
afterwards) — and "applied" must never be printed for cells that live only in a hidden
snapshot.

### L3 — Help → "What round-trips", the rail note and five greyed menu rows all claim a save drops charts, images, validation, filters and freeze panes. In the one-editor world the save keeps every one of them.
**Severity: LIES-TO-USER (under-promising, which is still false, and it drives the user away from the app).**

Measured: `QA-rich.xlsx` (chart, autofilter, data validation, hyperlink, freeze panes,
fill, second sheet) → open in the editor → change one cell → **our strip's Save** →
re-read the .xlsx:

| feature | before | after the editor's save |
| --- | --- | --- |
| `xl/charts/chart1.xml` | 1 159 B | **3 020 B, present** (plus a new `_rels`) |
| `autoFilter` | yes | **yes** |
| `dataValidation` | yes | **yes** |
| `hyperlink` | yes | **yes** |
| freeze `pane` | yes | **yes** |

The x2t round-trip preserves all of it. Meanwhile the live page says, verbatim:

* `?` → **What round-trips** → *"What a SAVE drops — charts, images, pivot tables,
  conditional formatting, data validation, comments, cell borders, freeze panes, filters,
  named ranges, macros."*
* the rail footer and the start-screen note: *"Complex styling may be simplified — keep
  your original file; Office saves copies."*
* Insert → **Chart** / **Image** / **Link**, Data → **Create a filter** / **Data
  validation**, File → **Make a copy** — all greyed, each with a tooltip citing the same
  false limit ("*LOffice's .xlsx round-trip does not model charts*").

Those sentences describe the **openpyxl** mapper, which in one-editor world only runs for
the Quick lane's bridge route (a `sort`) and the tier-1 fallback. The card for the bridge
route already says it correctly and locally; the global Help sheet does not.

**Correct behaviour:** the fidelity sheet must state the limit **per save path** — "the
full editor keeps charts, images, filters and validation; a change that has to go through
the file (a sort, or LOffice's own grid) does not" — and the Insert/Data rows that the
editor can do should stop citing a round-trip limit that no longer applies to them.

### L4 — "the agent edited this file — reloaded (pre-edit copy kept as X.pre-agent.xlsx)" is printed for *any* external change, including ones that made no such copy
**Severity: LIES-TO-USER.** Code-verified; the banner itself was not reachable in this
harness (see UNTESTABLE U1).

`extPlan()` fires on nothing but a newer `mtime`. Both of its sentences assert an agent
and a `.pre-agent.xlsx` safety copy:

* clean: *"the agent edited this file — reloaded (pre-edit copy kept as `<name>.pre-agent.xlsx`)"*
* dirty: *"… Either way the file as it was BEFORE the agent touched it is kept as `<name>.pre-agent.xlsx`."*

Only `office_ops`'s changeset-apply path writes that copy. Any other writer — Excel, a
script, `curl` on `/api/office/save`, a second LOffice tab, a `git checkout` — moves the
mtime and gets the same sentence, promising a file that does not exist. The dirty variant
is the dangerous one: it offers **Keep mine** on the strength of a backup that isn't there.

**Correct behaviour:** check whether `<name>.pre-agent.xlsx` actually exists before naming
it, and say "changed on disk by something outside LOffice" when the change cannot be
attributed to the agent.

### L5 — The AI panel's own intro promises an Undo and "the file only written when you press ⌘S". Both are false in the lane it describes.
**Severity: LIES-TO-USER.** Visible on the start screen and beside every conversation
(`qa-tpl.png`, right-hand panel):

> "You get a preview of every cell it would touch and it changes nothing until you press
> **Apply** — with an **Undo** after, and the file only written when you press ⌘S."

Measured: when the editor owns the document (i.e. always, once a workbook is open),
`ooActApply()` sets `card._undo = false` and `actLast = null`, so **there is no Undo
button on the card** — the undo is the editor's ⌘Z, which the card says but the intro does
not. And a plan containing a `sort` takes the bridge route, which **saves the file
immediately** (`/api/office/save` + a daily `.bak`) — the intro's "only written when you
press ⌘S" is exactly wrong for it. Worse, the promise is *sometimes* kept: the
create-from-nothing path (L2) does render an "Undo" chip, so the user cannot learn the
rule.

**Correct behaviour:** one sentence per lane that matches what the card will actually
offer — "Apply puts it in the editor; the editor's ⌘Z takes it back; ⌘S writes the file —
except a sort, which has to go through the file and is saved at once."

### L6 — The model is handed the last-saved file and told the user "is editing" it; the only staleness warning is eight characters of 10.5px dim text in an `overflow:hidden` span
**Severity: LIES-TO-USER.**

The prompt is `aiPreamble()` + the sheet dump. The preamble says *"The user is editing the
workbook “X”, on the sheet “Y”."* — and the dump is `snap`, read from **disk**, refreshed
at exactly two moments (open, save). With unsaved edits in the editor the model is
therefore shown the pre-edit file and told it is what the user is editing. Nothing in the
prompt says otherwise.

On screen, the entire warning is `aiPaint()` appending `· as last saved` to the context
chip (`#ai-ctxnote`: `font-size:10.5px; color:var(--dim); overflow:hidden`), i.e. the
`8×2` next to the SHEET pill in `qa-rich.png`. It is not in the answer, and the
transcript's own "context sent · 8×2" disclosure — the one place that answers *what did
the model actually get* — never records it. Save the file afterwards and the log keeps an
answer about data that was already stale when it was given, with no marker at all.

**Correct behaviour:** when `editorActive() && dirty`, put the staleness in the prompt
("the sheet below is the file as last saved; the user has unsaved edits") and label the
turn in the log ("asked against the last-saved sheet"), not only on a control the user has
to notice before pressing Ask.

### L7 — The unsaved-edits protection expires 15 s after the LOffice tab goes to the background
**Severity: LIES-TO-USER.** Code-verified end to end; the timing was not measured live
(see U1).

`pageTick()` opens with `if (document.hidden) return;`, so a hidden tab stops the
heartbeat keepalive, the mtime watch and the changeset recovery. `hbSync()` still rides
`paint()`, so a *change* is posted — but nothing re-posts, and
`office_ops.HEARTBEAT_TTL` is **15 seconds**. `visibilitychange` only calls `syncSkin`;
it does not force a beat or an `extCheck` on return.

So: unsaved edits in the editor → switch to another MOT Deck tab (or the OS hides the
webview) → 15 s later the bridge believes no page holds that workbook →
`APPLY_DIRTY_REFUSAL` ("*you have unsaved edits in that workbook — save it (⌘S) or close
it… Applying now would overwrite what you have not saved*") **does not fire** → pressing
Apply on a staged card overwrites the file and `ooReload()`s the editor over your unsaved
edits. Meanwhile `office_read`'s own result text keeps telling the model
"`unsaved_edits` true means a write tool will refuse until Debi saves", and
`office_ops.DIRTY_REFUSAL` promises the same. The guarantee is real only while the tab is
in front.

**Correct behaviour:** keep beating while hidden (a heartbeat is not a cadence
preference), or post a beat and run `extCheck()` on `visibilitychange` before anything can
be applied.

## BROKEN-FLOW

### B1 — Rename a workbook while the editor holds it and your unsaved work becomes unsavable
**Severity: BROKEN-FLOW (measured; `qa-rename.png`).**

1. Open `QA-A.xlsx`, make an edit (dot on).
2. Click the title → the rail's name box → **Rename** to "QA-A renamed".
3. Green message: **"Renamed to QA-A renamed.xlsx"**. Title updates. Dot stays on,
   deliberately ("a rename is not a save").
4. The editor was never told. `ooChild.probe()` still reports `doc: "QA-A.xlsx"`, and
   `ooDoc` is still the old name.
5. Press Save → `POST /api/office/writeback/QA-A.xlsx` → 404 →
   **"Not saved: no such workbook — the workbook on disk was not changed."**
   in our strip AND in the editor's own note.

There is no way out that keeps the work: the editor will keep saving to a name that no
longer exists, reopening discards the edit, and the message names no file and offers no
next step. The comment above `renameDoc()` says losing work to a rename "would be a very
expensive surprise" — this is more expensive: the work is kept and can never be written.

**Correct behaviour:** a rename must re-point the editor (`ooChild` needs a `rename(to)`
or the save must address the document by the parent's `current`), or the rename must be
refused while the editor holds unsaved edits, with the reason.

### B2 — The start-screen template cards are one-shot and then permanently dead
**Severity: BROKEN-FLOW (measured; `qa-tpl.png`).**

`newFromTemplate()` hardcodes the name ("Monthly budget", "Task tracker") and
`POST /api/office/new` refuses a name that exists (deliberately, for typed names). So
once you have made a Monthly budget, clicking the card forever gives the red line
**"a workbook with that name already exists"** — on a screen that is showing
`Monthly budget.xlsx` in its own recent list two inches below — with no way to name the
new one and no hint that renaming or deleting the old one is the fix. Blank is unaffected
(the empty name takes the ` (n)` walk).

**Correct behaviour:** templates should take the same never-clobber ` (n)` walk import
uses — "Monthly budget (2)" — or offer the name box pre-filled.

### B3 — The whole menu bar is hidden while a workbook is open, so most of the app's verbs have no reachable door
**Severity: BROKEN-FLOW.** `body.ooedit #menubar{display:none}` plus
`#toolbar{display:none}`, confirmed live (`menubar` computed `display:none` with the
editor up; `flex` with nothing open).

While a workbook is open, the only chrome is `☰ · LOffice · title · ⌂ · ? · Import · New ·
Save`. Survivor audit of the eight menus:

| verb | survives as | verdict |
| --- | --- | --- |
| File → Rename | click the title | ok |
| File → Save | strip Save / ⌘S | ok |
| File → Close file | ⌂ (start screen) | ok, different word |
| File → Download | rail row's `download` link only | ok but unlabelled as the only byte-exact copy |
| File → Delete | rail row's `delete` link only | ok |
| File → New / Import | strip buttons | ok |
| File → Make a copy | — | greyed anyway |
| **File → Back to MOT Main ↗** | **nothing** | **no survivor: you must close the workbook to leave the app** |
| Help → What round-trips, Keyboard shortcuts, About | `?` → About, with the other two as buttons | ok |
| Edit → Undo/Redo/Find/Replace/Clear cell | the editor's own ribbon | ok (different words, different scope) |
| View → File list / AI panel | `☰` and the pane tabs | ok |
| **View → Zoom, Gridlines, Show toolbar, Full width** | **nothing** | no survivor (the editor has its own zoom) |
| **AI → Ask / Show panel / Clear conversation** | panel's own `clear` and tab | mostly ok |
| **Data → Column statistics, Sort A→Z** | **nothing** | no survivor; sort is only reachable by asking the model |

And the mirror image: the bar is **only ever visible on the start screen**, where every
document row in it is disabled because nothing is open (`qa-tpl.png` — eight menus and
twelve toolbar buttons, all dead). Sixty-odd rows of chrome that can be seen only when
they can do nothing.

**Correct behaviour:** either keep our menu bar above the editor's ribbon with the rows
the editor does not cover (Back to MOT Main, Column statistics, Sort, Delete, Download,
What round-trips), or move those into the strip — but "hidden when useful, visible when
useless" is the one arrangement that cannot be right.

### B4 — File → Delete tells you to use File → Download first, at a moment when File → Download cannot be reached
**Severity: BROKEN-FLOW.** `mi-delete`'s sentence is *"Delete “X”? This cannot be undone —
File → Download first if you want to keep a copy."* Both rows live in the menu bar, which
is hidden whenever a workbook is open (B3), so the advice can only be read in a state
where it cannot be followed. **Correct behaviour:** name the control that exists at that
moment (the rail row's `download`), or put a "Download first" button in the same sentence.

### B5 — "This cannot be undone" — but a deleted workbook leaves its daily `.bak` behind, invisible
**Severity: BROKEN-FLOW / privacy.** Measured: deleting `QA-rich.xlsx`,
`Task tracker.xlsx` and `QA start create.xlsx` through the app's own Delete route left
`QA-rich.20260828.bak.xlsx`, `Task tracker.20260828.bak.xlsx` and
`QA start create.20260828.bak.xlsx` on disk. `is_backup_name()` filters them out of
`/api/office/files`, so the rail and the start screen show nothing — the copy is neither
listed nor deletable from the UI. The delete sentence is false in both directions: it
*can* be undone (from a file the user is not told about), and a user deleting a workbook
for privacy keeps its contents.

**Correct behaviour:** delete the workbook's backups with it, or say "a copy from earlier
today is kept as X.bak" and give the user a way to remove it.

## CONFUSING

### C1 — Clicking the row of the workbook you already have open, with unsaved edits, offers to discard them and "open" the file you are in
Measured: with `QA-A.xlsx` open and dirty, clicking its own rail row says
*"“QA-A.xlsx” has unsaved changes. Save it first, or click QA-A.xlsx again to discard
them."* with a **"Save & open QA-A.xlsx"** button. What the user actually gets by clicking
twice is a revert-to-last-saved, which is a reasonable thing to want and is not what the
sentence says. **Correct behaviour:** recognise `name === current` and offer
"Discard your changes and reload X from disk?".

### C2 — A staged agent card stays live after you switch workbooks; applying it changes a file you are not looking at and nothing on screen says so
Measured: the card correctly names its target (*"Hermes proposes 1 operation on
“QA-B.xlsx”"*) and survives a switch to another workbook with **Apply still enabled**.
`csApply()` posts by changeset id — the open file is irrelevant — and then calls
`ooExtReload(j.name)`, which **ignores `name`** when the editor is active and reloads the
*currently open* document instead. So the receipt appears, the sheet in front of you does
not change, and no sentence says the change landed elsewhere. **Correct behaviour:** the
receipt should say "applied to QA-B.xlsx, which is not the workbook you have open", with a
button to open it.

### C3 — A brand-new workbook is saved with "(a copy of the previous file is kept as …bak.xlsx)"
Measured on the Task-tracker template and on the create-from-nothing path: one second
after the file is created, the first save reports a safety copy of "the previous file" —
which is the empty workbook the create route just wrote. **Correct behaviour:** skip the
`.bak` line when the backup is of a file this session created.

### C4 — `.pre-agent.xlsx` safety copies are listed as ordinary workbooks
`Untitled.pre-agent.xlsx`, `ZZ final A.pre-agent.xlsx`, `S1 agent proof.pre-agent.xlsx`
sit in the file rail and in the start screen's *Recent spreadsheets* with size and date and
a `download`/`delete` pair, indistinguishable from real documents — and the sentence that
created them is long gone. `.bak` files are filtered; these are not. **Correct
behaviour:** filter them out of the rail and surface them where they mean something (the
external-change banner, an "agent backups" disclosure).

### C5 — The editor's right-hand cell-settings panel is open despite `hideRightMenu: true`, and takes ~300 px out of a three-column layout
`qa-rich.png`: with the rail (236 px) and the AI panel (334 px) on either side, the
editor's own Fill/Borders/Indent/Text-orientation panel occupies roughly a third of what
is left; the grid gets about eight visible columns on a 1440 px window. The config comment
says this default was chosen by looking at exactly this screenshot, so the flag is either
not taking effect in the vendored build or is being reopened by the selection. **Correct
behaviour:** verify the panel is closed after `onDocumentReady`, and close it there if the
config key does not hold.

### C6 — Deleting the open workbook from the rail while it has unsaved edits is a bare "sure?"
The rail/start-screen delete arms with the word `sure?` and no sentence — it mentions
neither that this is the file you are editing nor that unsaved edits go with it (the File
menu's version at least has a sentence, but see B4). **Correct behaviour:** the rail's
delete of `current` should borrow the File-menu sentence and add the unsaved-edits clause.

### C7 — The Agent lane's own description says the agent can write your workbooks
`agentGate()`'s "why", shown on the AGENT chip: *"Hermes, with the real Office tools: it
can read and write your workbooks itself, over several steps, and every write asks you
first."* Since the changeset ruling, **no tool on the loffice server can write** — the
model can only stage a proposal, and `/api/office/mcp` says so in its own `consent` block
("every tool on this server is read-only"). "Writes itself, and asks you first" is not
what happens; "proposes, and you apply" is. **Correct behaviour:** "it can read your
workbooks and propose changes; you apply them here."

## Untestable, and why

* **U1 — Anything on the page's 5 s/15 s tick.** `document.hidden === true` in the
  offscreen WKWebView probe, so `pageTick()` returns immediately and `tickN` stayed `0` in
  every run: the mtime watch (`extCheck`), the changeset recovery (`csTick`) and the
  heartbeat keepalive never ran. The change-driven heartbeat via `paint()` does fire
  (`hbLast` was populated). This is why L4 and L7 are code-verified rather than measured,
  and it is itself the evidence for L7. Testing them needs an on-screen webview.
* **U2 — The mtime 409 conflict from the editor.** Reachable in principle (open, let
  something else write, save) but every attempt in this run hit the 404 path first
  (B1) or raced the tick that was not running. The answer-in-place strip
  (`Overwrite it` / `Leave it alone`) is present in `oo.html` and our `ooSave()` correctly
  stays silent on 409 so as not to ask twice; unverified live.
* **U3 — ⌘S with keyboard focus inside the editor grid.** Synthetic `KeyboardEvent`s
  dispatched into the inner document did not reach sdkjs's handler (dirty stayed true), so
  this could not be measured directly. The control that L1 proves is labelled
  **"Save (Ctrl+S)"** by the bundle itself, so ⌘S-in-the-grid almost certainly shares the
  same false-clear — but it is inference, not measurement.
* **U4 — A real Agent-lane turn.** The AGENT chip was gated shut in this environment
  (`agentEnv.hermes` false — Hermes not running for this bridge), so the lifecycle tests
  were done by forcing `agentGate` open in the page and staging changesets through the
  real MCP tool. The end-to-end "model stages, card appears after the turn" path is
  unverified.
* **U5 — Bridge restart mid-session.** `./scripts/ship.sh` is off-limits for this pass.
* **U6 — Killing the llama runner.** Shared component; not touched. The panel's
  error-surfacing for a dead runner (`proxy_error` → "That did not work: …") is present in
  `aiSend` but unexercised.
* **U7 — Editor iframe / web-content-process crash.** `LOfficeEmbed.destroy()` exists and
  the parent has a fatal-error fallback, but no crash was induced; the parent's
  `clearWorkbook()` deliberately does *not* call `destroy()`, which is worth a separate
  look (the child keeps its document and `DOC` after a close — harmless in this run,
  since the next open is a swap).
* **Concurrency caveat.** Another builder was live on this bridge during the run (files
  appearing mid-probe: `Incident COPY.xlsx`, `Coercion proof.xlsx`, and changeset
  replacements). One agent-lane Apply failed with *"that change is no longer pending"* on a
